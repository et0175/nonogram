{# The puzzle player (TERM-037, FR-044, CARD-160) — not the uniqueness solver. The server renders the header and hands the puzzle to static/solver.js as one JSON payload (its shape is documented once, in solver.js's header). The board itself is drawn by solver.js from that payload and from the pure state module static/solver_state.js; the fallback paragraph below is what stays on screen when the script never ran. The payload carries the solution grid. That is allowed for this admin page only, behind the panel's door (ADR-0038/R6, CON-021); a public player must not ship it. The marking controls (CARD-161) are rendered here and start hidden; solver.js wires them and shows them once the board is drawn, so a page whose script never ran, or whose payload solver.js refused, shows no dead buttons (nor the usage hint below the board). Tools are toggle buttons (aria-pressed, exactly one pressed); undo, redo and reset stay focusable and say aria-disabled="true" when they have nothing to do. The "?" mark (CARD-186): a fourth tool, Maybe, follows Undecided. With it a click marks a cell "?" and a second click clears it; a drag paints "?". A click follows the selected brush (CARD-189): a first click gives the cell the brush's mark, a repeat click on it goes on along the brush's sequence (solver_state.js clickedState). So the tool group is "Marking tool", not "for drags" only, and the hint below the board names each sequence. Progress (CARD-162): the error counter sits in the toolbar row and is a live region (role=status), updated by solver.js after every recorded stroke. The solved banner is rendered here, hidden; it names the picture and takes the tools' place in the row while the board is solved. Since CARD-186 (review F-001) the tools and the banner's box share .player-slot (one grid cell, admin.css): solved, the tools are hidden but keep their box, so the toolbar keeps its rows and the board does not move (tested at 960..1480 px and 390 px; a picture name too long for the tools' box wraps and makes the row taller). The picture name is the answer (CARD-163, FR-044 AC-322/AC-323): the header and the tab title show the grid's width × height and its tier, never the name; the solved banner is the only place this page shows it. solver.js touches neither the header nor the tab title. Its text is announced through #puzzle-player-announce, a visually hidden live region that is always present (a region that only appears is not reliably read). Reset opens the in-page confirmation under it (role=alertdialog) instead of a browser confirm(). Hints (CARD-183): a Hint button closes the history group (its last child, after Reset and the confirmation) and a "Hints: N" counter (its own role=status region) is the element right after the error counter, shown to its right in the same row. Hint comes after Reset in the DOM, so the Tab order of the CARD-161 controls is unchanged (AC-310's order test). The counter's names are .player-hints / data-player-hints: "player-hint" is the usage paragraph below the board. Progress (CARD-187): "Progress: N%" (#puzzle-player-progress) is the element after the hint counter in the DOM. It is NOT a live region (no role, no aria-live, and neither wrapper has one): the percent changes on almost every mark and is read on demand. So the DOM/reading order (Errors, Hints, Progress) and the visual order (Progress, Errors, Hints) differ.
