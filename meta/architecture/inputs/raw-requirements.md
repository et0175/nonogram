# processed: 2026-08-31 → EC-007 (wording correction)
- AMENDS EC-007: its closing clause "refused before any conversion, dithering or solver work runs" is literally false on one path and must be narrowed to what the implementation can guarantee — "refused before any cropping, dithering or solver work runs". Loading and greyscaling are NOT refusal-free in general. Where a source's header extent and its decoded extent disagree, the refusal necessarily comes after `load_greyscale`, because the extent being judged is the one only the decode knows. Two disagreement classes measured on Pillow 12.3.0, CARD-026 review cycle 2, 2026-08-31: a PNG whose `eXIf` chunk follows `IDAT` (563x980 stored, 980x563 displayed — `Image.open` never reaches the chunk), and an orientation-tagged TIFF (60x40 + `tiffinfo={274: 6}` probes (40,60), decodes (60,40) — Pillow's TIFF reader applies the orientation at open and `ImageOps.exif_transpose` applies it a second time). The two-stage guard that creates this path is what makes CON-012 hold unconditionally: judging the header extent alone accepted a 15x30 request that retained only 0.287 of the displayed picture, a silent fail-OPEN. Cost of the narrowing, swept over all 441 grid shapes against the 563x980/980x563 disagreement: 105 accepted, 168 refused after the decode (the correct outcome), 168 false refusals — fail-CLOSED, each carrying an actionable message. Everything downstream of the decode (cropping, dithering, clue derivation, the solver) remains unreachable for every refused request, so the guarantee that matters is intact and only the word "conversion" was too broad (EC, correction). Source: meta/review/20260831T121656Z-CARD-026-cycle2.yml finding F-102, 2026-08-31.

CORRECTED 2026-09-01, before formalization: an earlier version of this entry argued for "longer side" on the grounds that NFR-005 derives cell size from max(width, height), so N would fix the printed cell size. **That is false and was measured to be false** — with the page turned to match the grid, a 20x10 prints 9.74mm and a 20x20 prints 6.43mm at the same N (a 51% spread), because the short side still consumes page through the clue gutter. - The derived side is `round(N * short/long)` of the source's own shape, clamped to MIN_SIZE at the bottom (FR/CON, technical). Source: brainstorm 2026-09-01. No clamp is needed at the top: the derived side is <= N <= MAX_SIZE by construction, which is the property that makes "longer side" the right reading of N. One sentence covers all three: N is the longer side, the other side follows the source's shape, and a shapeless source is square.
- The bottom clamp has a consequence that must be stated in the requirement rather than discovered: because the derived side cannot go below MIN_SIZE 10, the grid stops following the picture at `N:10`, and combined with FR-021's 2x rule **the widest picture accepted is exactly `N/5 : 1`** — 2:1 at `--size 10`, 4:1 at `--size 20`, 6:1 at `--size 30` (computed exactly, not sampled). So asking for a SMALLER puzzle refuses pictures a larger one would accept. Decision taken 2026-09-01: **refuse, and name the smallest N that would work** — e.g. "a 5:1 picture needs --size 25 or larger; at --size 15 the grid can only reach 15x10". FR-021's current message tells the user to crop the picture themselves, which is the wrong advice in this case: cropping is not what fixes it. Rejected alternatives: silently auto-bumping N (makes --size a request rather than an instruction), and lowering MIN_SIZE for derived sides (reopens CON-011's floor and produces thin strips whose solving experience nobody has evaluated).
- Page orientation must follow the grid's shape — wide grid to landscape, tall or square to portrait (NFR/CON, print). Source: brainstorm 2026-09-01. This is NOT a separable nicety once shapes are derived: a landscape picture at `--size 30` becomes a 30x10 grid, which prints at **2.29mm per cell on fixed portrait A4** and **6.60mm turned**. Deriving the shape without turning the page actively harms exactly the pictures the feature exists to help. Measured across shapes: 40x20 3.39 -> 5.00mm (+47%), 45x25 3.05 -> 4.40 (+44%), 60x10 2.29 -> 3.39 (+48%); tall grids keep portrait (20x40 4.91 portrait vs 3.22 landscape) and squares stay portrait by a small margin (30x30 4.40 vs 4.06). Note this interacts with the separate finding that NFR-005's `max(width, height)` model is not valid for rectangles at all — see the backlog entry and CARD-027's Architecture revision addendum.
- AMENDS NFR-005 and EC-008: printed cell size is NOT a declining function of `max(width, height)`, and the requirement must stop saying it is (NFR/EC correction, print geometry). Source: measurement 2026-09-01, surfaced while deciding `--size N`. On a fixed-orientation page a 40x20 and a 20x40 share `max() = 40` and print at **3.39mm** and **4.91mm** — so cell size is not a function of that term at all: 40 columns fight A4's 210mm axis while 40 rows get the 297mm one. A 40x20 even prints smaller cells than a 30x30 despite having fewer cells (800 vs 900). This is not merely imprecise, it makes EC-008's property (`PropertyTest_Layout_CellSizeNonIncreasingInLargerDimension`) ILL-POSED: two grids with the same `max()` produce different values, so the stated function does not exist. It is currently safe only because every grid this tool can produce is square — and FR-018/CARD-027 is the card that introduces rectangles, so it is the card that walks into it. Restate the property over the term that actually binds (cells along each page axis, given the orientation rule in the entry above), not over `max()`. Note the orientation rule and this correction are the same change viewed twice: once orientation follows the grid's shape, the longer grid side always maps to the longer page side, which is what makes a well-defined statement possible again.
