# ADR-0017: Export filename collision policy

**Status:** Accepted
**Date:** 2026-08-27
**Deciders:** Puzzle Creator (project owner)
**Revised:** —
**Migration:** —
**Pattern:** —
**API-Posture:** —

## Context

FR-015 gives every puzzle a name — auto-generated by default (the library key for library-sourced puzzles, or a mode+timestamp such as "random-2026-08-27-1430" for random/image-sourced puzzles) or overridden via a `--name` flag. FR-016 exports a finalized, uniqueness-confirmed puzzle as a PDF file on disk, and the PDF export filename is derived from that same puzzle name (DEC-016). Because the CLI is a single-process tool with no persistent database of prior exports (CON-001), the only way to detect a naming collision at export time is to check whether a file of that name already exists in the target directory.

Two distinct situations can produce a collision: a user deliberately reuses `--name` across runs (e.g. re-exporting after a tweak), or an auto-generated name repeats — which is more likely for library-sourced puzzles (the library key is stable and finite) and, at minute precision, is possible even for random/image-sourced puzzles (see DEC-018). In either case, the tool must decide what happens when the computed export path already points at an existing file: overwrite it, refuse and error out, or find a non-colliding path automatically. The decision must not silently destroy a prior export the user may still need (FR-016's purpose is to hand the user a durable artifact), while also not introducing friction severe enough to discourage the repeated re-runs this single-user CLI is expected to support (US-011, US-012).

## Decision

We will auto-suffix. When the computed export path for FR-016 already exists on disk, the tool appends an incrementing numeric suffix ("-1", "-2", ...) to the filename (before the extension) and retries until it finds a path that does not collide, then writes the PDF there without prompting or failing. This satisfies FR-015/FR-016 because it guarantees every export call succeeds and produces a durable, non-destructive artifact regardless of whether the collision came from a reused `--name` or a repeated auto-generated name, with no added flag or interactive step for the user to manage.

## Alternatives considered

### overwrite

Silently overwrite the existing file at the computed path. This was rejected because it risks silent data loss: a user who re-runs the tool without realizing a prior export already occupies that filename would lose that earlier PDF with no warning, which conflicts with FR-016's purpose of producing a durable, retrievable artifact.

### error

Reject the export with a "file already exists" error, forcing the user to pick a different `--name` or delete the old file before retrying. This was rejected because it adds friction to the common single-user workflow of intentionally re-running or re-exporting the same puzzle (e.g. after adjusting a parameter and regenerating), and it does so even in the ordinary case of an auto-generated name repeating, which the user did not consciously choose and may not expect to have to resolve manually.

## Consequences

### Positive
- Every export call in FR-016 succeeds without ever destroying a previously exported file, closing the same silent-data-loss gap that DEC-016's collision cases were flagged as creating.
- The user experiences no added friction, flag, or prompt when re-running or re-exporting a puzzle — collisions are resolved transparently, which matches how a single-user CLI is used repeatedly during iteration (US-011, US-012).
- The same mechanism resolves both collision sources uniformly — a reused `--name` and a repeated auto-generated name (including the same-minute case DEC-018 addresses) — without requiring separate handling logic for each.

### Negative
- Repeated re-runs without the user noticing can silently accumulate a growing series of similarly-named files ("puzzle-1.pdf", "puzzle-2.pdf", ...) in the export directory, which the user must eventually notice and clean up manually — there is no warning that this is happening.
- The suffix-search loop (checking path existence, incrementing, retrying) is new export-path logic that FR-016's file-writing code must implement and test; unlike the overwrite alternative, it cannot simply hand a fixed path to the PDF writer.

### Neutral
- The exported filename a user sees is no longer guaranteed to exactly match the puzzle name plus extension (DEC-016) — it may carry a numeric suffix — so any documentation or examples of expected output filenames must account for the possibility of a suffix.
- This decision composes with DEC-016 (filename convention) and DEC-018 (auto-generated name precision): whichever alternative those resolve to, this ADR's suffix mechanism is the fallback that runs whenever the resulting computed path still collides.
